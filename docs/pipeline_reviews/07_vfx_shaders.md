### Per-candidate output structure

Each candidate dir has:
- `<id>.gdshader` — real shader code, generated from template + mutated params

- `flipbook.png` — animated atlas
- `frames/frame_NNN.png` — per-frame CPU renders (3-6 frames typical)
- `project.godot` — minimal Godot project for opening the .tscn standalone

## What works

- ✅ **Real shader-iteration framework.** Real templates (`canvas_item` shaders that compile in Godot), real param mutation, real CPU proxy renders, real scoring metrics, real promotion workflow, real LLM review packets, real per-candidate Godot scenes ready to open.
- ✅ **Non-OCR scoring is mature.** 12 image metrics (coverage, contrast, edge_energy, colorfulness, motion, flicker, clip_high/low, center_distance, aspect, frames, mean_alpha) + role-specific gates. **This is real CV-based shader QC**, not "let an LLM read screenshots."
- ✅ **Auto-hints are concrete.** "Coverage low: increase radius/thickness/edge_width/opacity" — actionable parameter advice driven by which metric failed which gate.
- ✅ **LLM review packet (JSON) is a clean interface.** Top candidates extracted with score + grade + metrics + hints + gate issues. **An LLM can iterate on shader params against this packet without seeing screenshots.**
- ✅ **Promotion + diversity filtering exists.** `shader_promote.py` shortlists top-scoring candidates with diversity-distance constraint to avoid near-duplicates filling the queue.
- ✅ **Reference scoring infrastructure exists.** `shader_reference_score.py` scores against curated images. The framework supports it — just not used yet.
- ✅ **Godot CLI render wrapper exists.** `shader_godot_render.py` can replace CPU proxies with real Godot renders if the Godot binary is available. Plumbed but defaults to CPU proxy.
- ✅ **Cleanest separation in the project** between **lab** (parameter iteration), **review queue** (human shortlist), and **production** (when promoted, lands somewhere it can ship).

## What's open / weak

1. **Every batch is a smoke test.** All 5 batch IDs include `smoke` or `mutate` — no batch was named for a real game-design target. **Nothing has been *iterated on* against a real reference image.** The framework can do it; nobody has.
2. **128×128 preview is too small to judge real visual quality.** All previews are 128² CPU proxy renders. Real Godot render at 512² would tell you much more.
3. **3-6 frames per candidate is too few to judge motion.** Real flipbook animations are 16-32 frames. The smoke tests baked thin animations to save time.
4. **Reference set is a single image.** `smoke_portal_ref/ref_001.png`. Reference-driven evolution can't really kick in until there are actual curated style references (8-12 images per intent).
5. **No real promotion to production.** Even the "keep" candidates from review queues haven't moved into a shipping shader directory or into the Godot project for use.
6. **Top-scored smoke candidate had 3 gate warnings.** Score 90 sounds high; the metrics show coverage 9% (way low for portal), contrast 0.02 (way low), motion 0.01 (almost static). The scoring rewards "shader compiled and produced output" more than "shader looks good."
7. **Templates list is incomplete per the lane's own README.** Pending per `SHADER_WORKFLOW_STATUS.md`: spatial templates (force fields, water, energy weapons, terrain overlays), particle process shaders (orbitals, sparks, embers, swarms).
8. **`macro_detail_v1.gdshader` is homeless.** It's a terrain shader living in the VFX-shader lane because of a worldgen leftover. Doesn't belong here.
9. **Pending: validated Godot-rendered flipbook bake on this machine.** Per `SHADER_WORKFLOW_STATUS.md`. Means the Godot CLI render path has never been confirmed end-to-end.
10. **Templates (6) are on-theme but generic.** Portal swirl, ring field, beam, shield, dissolve. **Missing common needs:** ground glow, AOE indicator, status-effect halo, weapon trail, projectile trail, hit flash, healing rising-particles equivalent, dash motion blur, chargeup pulse.

## Pipeline-level read

- **State:** **the most disciplined-on-paper iteration framework in the project**, but **no batch has been pointed at a real production target yet.** Every output is a smoke test.
- **Strongest part:** **the scoring + auto-hints + LLM review packet loop.** This is genuinely well-designed. CV-metric gates that drive actionable parameter advice → an LLM can iterate without seeing pixels. **The framework is ready for real use.**
- **Weakest part:** **48 candidates of nothing in particular.** No reference set has more than 1 image, no batch had a real intent beyond "test the framework." All "production" batches don't exist.
- **What "shipping quality" would require:**
  - Pick 5-8 real shader needs (e.g. "fire AOE ground decal", "frost shield ripple", "level-up particle ring", "weapon trail", "hit flash"). Define each as a role.
  - Build 8-12 image reference sets per role. Curate from games/concept art that match the look.
  - Run `shader_evolve.py` against each role with population=36 and generations=5.
  - Promote 4-6 candidates per role into a review queue. Pick winners.
  - **Standardize a "production shaders" directory** outside the lab where promoted shaders land for use in the actual game.

## Concrete next moves

1. **Run a real (non-smoke) evolution batch.** Pick *one* effect — e.g. fire impact ring — build a 6-image reference set, run `shader_evolve.py` with the right intent + role, see if the framework actually delivers. ~30-60 min. **The most valuable test for this pipeline right now**, exactly parallel to "multi-prop generalization test" for props.
2. **Increase preview size to 256² or 512² for any real batch.** 128² hides too much. CPU render time scales but is still fast.
3. **Build 5-8 reference sets** matching the actual effects the game needs. This is the unblocking prerequisite for #1.
4. **Decide where promoted shaders go.** Currently they sit in `review_queues/` indefinitely. Need a "shipped" or "in_use" directory for shaders the game actually uses.
5. **Move `macro_detail_v1.gdshader` out of `art_lab/shaders/templates/`** — either to `pipelines/textures/shaders/` (it's a terrain material shader) or hand it to whatever new worldgen lives at `world3/`.
6. **Add the missing common templates:** ground_glow, aoe_indicator, weapon_trail, projectile_trail, hit_flash, status_halo, dash_blur, charge_pulse. These are the bread-and-butter shaders most games need that aren't in the current 6.

## Cross-lane note

The framework here is **better-designed than the `pipelines/vfx/` content baker** for iteration purposes. The shader lane has scoring + gates + auto-hints + diversity filter + reference scoring + LLM review packets. The bake lane has effect.json schema + manifests + flipbooks but no equivalent iteration loop.

If you ever want to upgrade the bake lane's authoring workflow, **steal patterns from this lane**, particularly the score-based grading and LLM review packet format.
