# Phase B — Multi-Resolution Texture Pipeline (Design)

**Status:** design / pre-implementation
**Date:** 2026-05-07
**Owner:** world3 / pipelines/textures
**Successor to:** Phase A polish (A.7 → A.11)
**Related ROADMAP entry:** `world3/docs/ROADMAP.md` Phase B (will be rewritten to reflect this design)

---

## Summary

Phase B builds the **full multi-resolution texture tree** — every shipping
material gets generated at its native resolution, super-resolved up to a
4K working master, has its physically-derivable maps (normal, AO,
roughness micro-detail) re-baked at the working resolution, then
filtered down into a mip ladder of physically-correct outputs (4K /
2K / 1K / 512). Godot picks the right tier per use case.

**The animating principle (per project owner):** spend the time now
to build the full tool tree. Have as many decision branches as we
can, then pick the right path per material. Quality means *physical
correctness and visual fidelity*, not just pixel count.

Reframed from the original ROADMAP entry, which scoped Phase B as
"build an upscaler." That's tier 2 of a 5-tier tree:

1. **Generation** — native-res producers (mostly built in Phase A polish)
2. **Upscaling** — 512→1K/2K/4K with tile preservation (NEW)
3. **Bake / re-derive** — high-res normal-from-height, AO, roughness
   micro-detail (NEW — conceptually novel piece)
4. **Mip ladder** — multi-tier physically-correct outputs per material (NEW)
5. **Per-tier QA** — extension of existing A.7 richness gate (extension)

The full tree is the deliverable. Phase B decomposes into B.1 → B.6
(mirroring the A.7 → A.11 polish sequencing pattern).

---

## Goals

- Every shipping texture has a **mip ladder** (4K master + downsampled
  runtime tiers) where every map is physically correct at every tier.
- The ladder is generated by **baking at high res then filtering
  down**, not by generating at each tier independently. AO and
  normals especially benefit from this.
- **Generation resolution and ship resolution are independent dials.**
  Generate cheap, ship at any tier. Generate at hero res, ship at any
  tier. The bake/downsample step bridges the gap.
- All five backends (`derive`, `sm`, `chord`, `chord_sm_rough`,
  reference-anchored) flow through the same multi-resolution pipeline.
- Per-tier QA (richness gate, tile_2x2, sphere/plane previews,
  cross-tier contact sheet) so we can verify each tier visually.
- One canonical orchestrator command (`aaa_texture.py`) that produces
  the full tree end-to-end, plus standalone tools for each tier so
  individual stages can be re-run.

## Non-goals

- **Native generation above 1024.** CHORD already runs at 1024;
  pushing FLUX to native 2K is out of scope (token budget, model
  behavior unproven, slow). The 4K master is *upscaled*, not native.
- **Phase E (per-mode material tuning).** Phase B writes the ladder;
  Phase E binds per-mode `.tres` files to the right tier. Tight
  coupling but separate phase.
- **Phase F (LOD / streaming).** The mip ladder will eventually feed
  Godot LOD when Phase F lands, but Phase B does not implement LOD.
- **OpenTopo branch synergy.** Bake-at-high-res tooling could be
  reused for OpenTopo's "baked ground from orthophoto" work, but
  OpenTopo is a separate branch with its own roadmap. Out of scope.
- **Macro variation / per-game-mode tuning.** Phase D and Phase E.

## Foundations consumed from Phase A polish

- **A.7 richness gate** (advisory) — runs at every tier so smooth-A
  failures get caught at every resolution.
- **A.8 CHORD backend** — produces 1024-native sharp normals/heights;
  natural pairing with SR (1K → 4K is a 4× upscale, not 8×).
- **A.10 reference-anchor mode** — anchored generation flows through
  the same SR/bake/mip pipeline; no special-case wiring needed.
- **A.11 chord_sm_rough hybrid** — primary backend for hero rock
  materials. The flagship ladder (rock_dark full 512→4K + bake + mip)
  uses this.
- **BasicScheduler swap** (A.10c infrastructure) — relevant if SR via
  FLUX img2img uses partial denoise; we already know the scheduler
  honors `denoise` correctly.

## The 5-tier tree (reference)

```
Generation                          Upscaling                  Bake / re-derive            Mip ladder              QA
──────────                          ─────────                  ──────────────────          ──────────              ──
derive   (512)  ┐                                                                                                  ┐
sm       (512)  ├──► (already      ┌──► Real-ESRGAN          ┌──► normal from         ┌──► 4K master         ┌──► richness
chord    (1024) │    here)         │    (general SR,         │    upscaled height     │                      │    (per tier)
chord_sm_rough  ┤                  │    fast, cheap)         │                        ├──► 2K runtime        │
   (1024)      │                  ├──► SwinIR / BSRGAN       ├──► AO from upscaled   │                      ├──► tile_2x2
                │                  │    (alt SR profiles —   │    height (re-bake     ├──► 1K runtime        │    (per tier)
                │                  │    if survey supports)  │    integral at high   │                      │
+ A.10 anchor   ┘                  │                         │    res, then mip)     ├──► 512 runtime       ├──► sphere / plane
                                    └──► FLUX img2img heal    │                        │                      │    previews
                                         (existing            ├──► roughness micro-   └──► all written        │
                                         flux_upscale.py —    │    detail re-bake          per material        └──► cross-tier
                                         tile-aware via       │    from 4K albedo                                   contact sheet
                                         offset+heal trick)   │                                                     (NEW)
                                                              └──► curvature/cavity
                                                                   (if useful)
```

Every material flows L→R. Generation tier picks the source; upscaling
takes it to a 4K working res; bake re-derives the physically-derivable
maps at 4K; mip ladder writes filtered tiers; QA gates every tier.

### B.1 — SR survey + first SR tool

**Why first:** can't bake or mip without a working upscaler. SR is the
most uncertain piece (multiple model families, install complexity,
tile-aware vs. tile-agnostic decision). Survey first, then commit.

**Scope:**
- New survey doc `pipelines/textures/EXTERNAL_SR_TECHNIQUES.md`
  (parallel structure to the existing `EXTERNAL_TECHNIQUES.md` from
  A.5). Cover Real-ESRGAN, SwinIR, BSRGAN, ComfyUI's UltimateSDUpscale,
  tile-aware SR variants, FLUX img2img-as-SR (already in
  `flux_upscale.py`).
- Decision: **first SR backend = Real-ESRGAN** unless survey
  surfaces a clearly better default. Reasons: GPL-permissive, fast
  (~5s per map at 4×), well-maintained, ComfyUI's
  `UpscaleModelLoader` accepts the .pth directly, multiple model
  variants for material classes (`RealESRGAN_x4plus`,
  `RealESRGAN_x4plus_anime_6B`, `realesr-general-x4v3`).
- Install model into `D:/assets/animators/ComfyUI/models/upscale_models/`
  (currently empty — placeholder file only).
- New tool `pipelines/textures/sr_upscale.py` — single-map SR via
  ComfyUI's UpscaleModelLoader. Tile-preservation strategy: SR is
  patch-based, so feeding a tileable image to Real-ESRGAN
  *usually* preserves tiling, but at boundaries some models break it.
  Apply the same offset+heal trick `flux_upscale.py` uses if needed.
- Audit `flux_upscale.py` — keep as a heal-pass tool, not the primary
  SR. It's albedo-only and slower than Real-ESRGAN. Document the
  division of labor: Real-ESRGAN for SR proper, FLUX img2img heal
  for "polish a near-shipping image at the same res."

**Deliverables:**
- `pipelines/textures/EXTERNAL_SR_TECHNIQUES.md`
- `pipelines/textures/sr_upscale.py`
- A/B contact sheet under
  `world3/docs/captures/phase_b/B1_sr_survey/` showing Real-ESRGAN
  vs. Lanczos vs. flux_upscale on 3 representative materials
  (rock_dark, snow, leaf_litter).
- `TOOLS.md` entry, `RECIPES.md` entry, `TEXTURE_RND.md` "B.1" entry.

**Exit:** `python sr_upscale.py --in albedo.png --out albedo_4k.png
--scale 4` works on a tileable input and the output stays tileable
(measured by `edge_seam_score`).

**Estimate:** half session.

### B.2 — `bake_pbr.py` — high-res re-derive

**Why second:** depends on B.1 (need the upscaled albedo + height).
This is the conceptually novel piece — most of the value of "high-res
master then mip down" comes from baking at high res, not from the SR
itself.

**Scope:**
- New tool `pipelines/textures/bake_pbr.py`. Inputs: an upscaled
  albedo + upscaled height. Outputs: re-derived normal, AO,
  roughness-micro-detail at the working resolution.
- **Normal from height**: Sobel or Scharr filter on the 4K height,
  proper precision (float32, signed gradient), then encode to
  tangent-space normal. Sub-texel accurate vs. SR'd normal.
- **AO from height**: re-bake at 4K. AO is an integral over the
  hemisphere — much smoother and more accurate at 4K than at 512.
  Use `derive_pbr_v2.py`'s existing AO logic but at 4K. Optionally
  upgrade to a proper raymarched AO if the existing heuristic isn't
  good enough at 4K (decision after first A/B).
- **Roughness micro-detail**: this is the subtle one. The SR'd
  roughness is "detailed" but it's hallucinated by the upscaler. The
  *physically correct* roughness comes from re-baking from the
  upscaled albedo's micro-luminance variation + the 4K height's
  curvature. Compose: `roughness_4k = SR(roughness_512) * 0.5 +
  derive_from(albedo_4k, height_4k) * 0.5` or similar. Calibrate
  empirically.
- Backend-aware: when source is `chord_sm_rough`, *trust the SM
  roughness* and only re-bake what wasn't generated correctly
  (normal benefits from re-derivation even from CHORD's good 1K
  normal, because we're going to 4K).
- **Map ownership table** — extend the RECIPES.md backend table to
  include "post-bake at 4K":

  | Map | derive | sm | chord | chord_sm_rough | bake @ 4K result |
  |-----|--------|----|----|----------------|------------------|
  | albedo | delight | SM | CHORD | CHORD | SR'd, no re-bake |
  | normal | sobel(h) | SM | CHORD | CHORD | re-derived from 4K height |
  | roughness | preset | SM | CHORD | SM | re-derived from 4K albedo+height |
  | metallic | ~0 | SM | CHORD | CHORD | SR'd, no re-bake (low-freq, fine) |
  | height | freq split | SM | CHORD | CHORD | SR'd, no re-bake |
  | ao | blur(curve) | from h | from h | from h | re-baked from 4K height |

**Deliverables:**
- `pipelines/textures/bake_pbr.py`
- A/B contact sheet under
  `world3/docs/captures/phase_b/B2_bake_ab/` showing
  SR-only vs. SR+bake on 3 representative materials.
- `TOOLS.md` entry, `RECIPES.md` entry, `TEXTURE_RND.md` "B.2" entry,
  `DECISIONS.md` entry on the bake-at-high-res rationale.

**Exit:** A/B shows SR+bake produces cleaner normals (sharper
gradient, less SR hallucination) and smoother AO (visible at any
viewing distance) than SR alone. Decision: bake-by-default.

**Estimate:** full session.

### B.3 — `mip_ladder.py` — multi-tier output writer

**Why third:** depends on B.1+B.2 (need a 4K baked master to mip
from). Cheapest tier in compute — pure filtering. The "free quality
insurance" piece: once we've done the expensive work, writing extra
tiers costs almost nothing.

**Scope:**
- New tool `pipelines/textures/mip_ladder.py`. Input: a 4K PBR set
  (the baked master from B.2). Output: 2K, 1K, 512 tiers, all
  physically correct because they were filtered from a high-res bake.
- **Per-map filtering rules:**
  - **Albedo**: box or Lanczos filter (gamma-aware: linearize →
    filter → re-encode sRGB).
  - **Normal**: filter the *vector field*, not RGB channels
    independently. Specifically: decode → filter XYZ as floats →
    renormalize → re-encode. Naive RGB filtering produces shorter
    normals at lower mips (faded look).
  - **Roughness**: filter as luminance, but consider Toksvig-style
    normal-variance compensation — when normals get filtered down,
    the surface's *effective* roughness goes up. Optional: bump
    roughness up at lower mips proportional to the local normal
    variance. Document, gate behind a flag, evaluate after first A/B.
  - **AO**: linear filter, no special handling.
  - **Metallic**: nearest or box (binary-ish, don't blur edges).
  - **Height**: linear filter (don't lose dynamic range; preserve
    float precision intermediate).
- Output layout: extend the existing `world/textures/library/<id>/`
  pattern. Either separate dirs (`<id>/4k/`, `<id>/2k/`, `<id>/1k/`,
  `<id>/512/`) or a flat naming convention (`<id>_<map>_4k.png`,
  etc.). Pick after one round of usage. Default: separate dirs
  (cleaner, mirrors the QA dir pattern).
- Each tier gets its own `qa/` subdir with tile_2x2, sphere/plane,
  seam_score, sanity, richness — wire B.4 into this.

**Deliverables:**
- `pipelines/textures/mip_ladder.py`
- Visual A/B under `world3/docs/captures/phase_b/B3_ladder_ab/`
  showing each tier of one material side-by-side.
- `TOOLS.md` entry, `RECIPES.md` entry, `TEXTURE_RND.md` "B.3" entry.

**Exit:** Running `mip_ladder.py --in <4k_dir>` produces 4K/2K/1K/512
copies of all 6 maps; visual review confirms downsampled tiers look
correct (no normal-fading, no albedo-darkening, no AO discontinuities).

**Estimate:** half-to-full session.

### B.5 — Orchestrator integration + flagship ladder

## Operating principles applied

- **One thing at a time** — B.1 → B.6 sequenced so each step's
  output feeds the next.
- **Improve what we have before extending** — `flux_upscale.py` is
  audited and kept where useful (heal pass), not replaced wholesale.
- **Research before building** — B.1 is research-first; install
  decision is gated on survey results (per memory rule
  "research before installing").
- **Tools and workflows over output** — Phase B builds infrastructure
  every future material benefits from. Rock_dark flagship is the
  proof, not the only output.
- **Document as we go** — RECIPES, TOOLS, PIPELINE, TEXTURE_RND,
  LESSONS, DECISIONS all updated per step.

## Risks + mitigations

- **SR breaks tiling at boundaries.** Mitigation: offset+heal trick
  (already proven in `flux_upscale.py`); per-tile `edge_seam_score`
  measurement at every tier; fallback to FLUX img2img heal pass if
  Real-ESRGAN consistently breaks tiling.
- **High-res bake of AO is slow.** Mitigation: existing AO derivation
  in `derive_pbr_v2.py` is fast (it's a heuristic on height); only
  upgrade to raymarched AO if first A/B shows the heuristic is
  insufficient at 4K. Flag-gated.
- **Mip filtering of normals or roughness produces visible artifacts
  (faded normals, wrong roughness at distance).** Mitigation:
  vector-field filtering for normals (mandatory); Toksvig
  compensation for roughness (gated, evaluated after first A/B).
- **Disk usage explodes.** Estimate: ~30 textures × 6 maps × (4K +
  2K + 1K + 512) ≈ 9-12 GB. D: has 232 GB free. Acceptable. Re-check
  if the wgv3 set grows past ~80 textures.
- **Richness threshold drift across resolutions.** Mitigation: B.4
  calibrates per-resolution thresholds against actual generated
  ladders before promoting from advisory to gate.
- **Real-ESRGAN hallucinates wrong micro-detail (especially on
  materials with strong domain-specific textures like snow or
  vegetation).** Mitigation: B.2's bake step re-derives the
  physically-derivable maps from the SR'd albedo/height — even if
  the SR hallucinates, the bake produces consistent normal/AO/
  roughness. Flagship A/B in B.5 confirms.
- **`chord_sm_rough` at 1024 → 4K SR has only 4× scale to play with;
  Real-ESRGAN's 4× model is the natural fit, but if we want 8K
  hero output, need a 2× chained or a different model.** Defer to
  B.6 if 8K demand surfaces.

## Open questions to resolve during implementation

- Output layout: separate `<id>/4k/`, `<id>/2k/` dirs vs. flat
  `<id>_<map>_4k.png` naming. Default: separate. Decide after first
  ladder ships (B.3).
- Where does the "bake at 4K then mip" happen for materials generated
  with the speed preset (`--quality fast`)? Default off (no ladder
  for speed mode). Decide if there's value in a "bake-only" path
  (skip SR, bake at gen res, mip down) for fast-mode iteration —
  probably YAGNI; defer.
- Do we delete the 4K master after writing the ladder (save ~70%
  disk per material) or keep it as the canonical source of truth?
  Default: keep. Cheap insurance against re-baking.
